# Mini Git

커밋을 **작은 기록 카드**, 브랜치를 **카드에 붙이는 이름표**라고 생각해 보세요.
이 프로그램은 카드를 만들고, 카드 사이의 관계를 따라가며 Git의 기본 원리를 배우는 연습 도구입니다.

실제 파일 내용, 원격 저장소, 파일 저장 기능은 다루지 않습니다. 프로그램을 종료하면 기록이 사라집니다.
Python 3.10 이상만 있으면 됩니다. 추가 패키지는 필요하지 않습니다.

## 실행하기

프로젝트 폴더에서 실행하세요.

```sh
python main.py
```

다음 명령을 한 줄씩 입력해 보세요. `mini-git>`는 프로그램이 보여 주는 표시이므로 입력하지 않습니다.

```text
init "김 민수"
commit "처음 시작"
branch feature
switch feature
commit "로그인 기능 추가"
switch main
commit "결제 기능 추가"
log
path 00000002 00000003
ancestors 00000003
search "기능"
search "로그인 기능"
search --author="김 민수"
log --sort-by=date
log --sort-by=author
exit
```

이 예시의 커밋 관계는 다음과 같습니다.

```text
00000001 처음 시작
├── 00000002 로그인 기능 추가  ← feature
└── 00000003 결제 기능 추가    ← main (현재 브랜치)
```

`PATH` 결과는 `00000002 → 00000001 → 00000003`입니다.
`ANCESTORS 00000003`은 `00000001`을 보여 줍니다.
`SEARCH "기능"`은 두 번째와 세 번째 커밋을 보여 줍니다.

## 명령어

| 명령어 | 하는 일 |
| --- | --- |
| `INIT "이름"` | 저장소와 main 브랜치를 만들고 작성자를 정합니다. |
| `BRANCH 이름` | 현재 커밋을 가리키는 브랜치를 만듭니다. |
| `SWITCH 이름` | 현재 브랜치를 바꿉니다. |
| `COMMIT "메시지"` | 현재 브랜치 끝에 새 커밋을 붙입니다. |
| `LOG` | 모든 브랜치의 커밋을 부모가 먼저 나오도록 보여 줍니다. |
| `LOG --sort-by=date` | 날짜가 이른 것부터 보여 줍니다. |
| `LOG --sort-by=author` | 작성자 이름의 문자열 순서로 보여 줍니다. |
| `PATH 번호1 번호2` | 부모와 자식 사이를 양방향으로 이동하는 가장 짧은 길을 찾습니다. |
| `ANCESTORS 번호` | 자신을 제외한 모든 조상을 한 번씩 보여 줍니다. |
| `SEARCH "단어 또는 구절"` | 메시지의 단어나 이어진 구절을 찾습니다. |
| `SEARCH --author="이름"` | 작성자 이름이 정확히 같은 커밋을 찾습니다. |
| `exit` 또는 `quit` | 종료합니다. |

- 명령어는 대소문자를 구분하지 않습니다. 이름과 옵션은 입력한 대소문자를 사용합니다.
- 공백이 있는 인자는 따옴표로 감싸세요. 빈 이름과 빈 메시지는 받지 않습니다.
- 메시지 검색은 대소문자를 무시하고 공백으로 단어를 나눕니다. `login`은 `LOGIN`에 맞지만 `log`에는 맞지 않습니다. 문장부호는 단어에 남습니다.
- 여러 단어를 검색하면 공백 종류와 개수를 통일한 뒤 이어진 구절을 찾습니다.
- 정렬 기준이 같으면 생성 순서를 유지합니다. 정렬 옵션은 부모 우선보다 지정한 기준을 우선합니다.
- 경로가 없으면 `No path`, 결과가 비어 있으면 `No commits`를 출력합니다.
- 같은 시작점과 끝점의 경로는 해당 커밋 하나입니다. 조상 목록의 순서는 보장하지 않습니다.
- 커밋 전에도 브랜치를 만들 수 있습니다. 이때 각 빈 브랜치에서 커밋하면 서로 연결되지 않은 출발점이 생깁니다.
- `INIT`은 실행 중 한 번만 가능합니다. 다시 입력하면 기존 기록을 지키고 오류를 보여 줍니다.
- 커밋 번호는 1부터 증가하는 수를 16진수로 표시합니다. 실제 Git의 내용 기반 해시는 아니며, 미션에서 허용한 카운터 방식입니다. 전체 번호를 입력하세요.
- 시간은 시간대 혼동을 피하도록 UTC로 기록하며 `+00:00`으로 표시합니다.

## 코드를 읽는 순서

1. `repository.py`의 `Commit`: 기록 카드에 어떤 정보가 있는지 확인합니다.
2. 같은 파일의 `Repository`: 이름표를 붙이고 옮기는 과정을 읽습니다.
3. `algorithms.py`: 정렬하고 길을 찾는 방법을 읽습니다.
4. `repository.py`의 `SearchIndex`: 찾아보기를 만드는 방법을 읽습니다.
5. `main.py`: 입력한 글자가 함수 호출로 바뀌는 과정을 읽습니다.

## 핵심 원리

### 커밋 그래프와 DAG

커밋은 `hash`, `message`, `author`, `timestamp`, `parents`를 가집니다.
`commits` 딕셔너리는 번호로 카드를 바로 찾는 보관함입니다. 평균 조회 시간은 O(1)입니다.
`branches`는 브랜치 이름과 마지막 커밋 번호를 연결합니다. `head`는 현재 브랜치 이름입니다.

새 커밋은 이미 존재하는 커밋만 부모로 삼습니다. 기존 카드의 부모는 바꾸지 않습니다.
그래서 부모 방향으로 계속 가도 출발점으로 돌아올 수 없습니다.
이렇게 방향이 있고 순환이 없는 그래프를 **DAG**라고 합니다.

부모 필드는 여러 번호를 담을 수 있고, 탐색 함수도 여러 부모를 처리합니다.
미션의 `COMMIT` 명령은 부모가 없거나 하나인 커밋만 만듭니다. 병합 명령은 추가하지 않았습니다.

### 부모 먼저 출력: 위상 정렬

각 카드에 아직 출력하지 않은 부모 수를 적습니다.
그 수가 0인 카드를 먼저 출력하고, 그 카드의 자식들이 기다리는 부모 수를 하나씩 줄입니다.
모든 부모가 나온 자식만 차례를 얻습니다.

### 가장 짧은 길: BFS

출발점에서 한 칸 거리, 두 칸 거리 순서로 찾아갑니다.
먼저 발견한 길이 가장 짧은 길입니다. 이를 **너비 우선 탐색(BFS)**이라고 합니다.
이웃을 경로 문자열의 사전순으로 살펴보므로, 같은 길이의 경로 중 사전순으로 가장 작은 길을 고릅니다.
어디에서 왔는지 저장해 두었다가 도착점에서 거꾸로 따라가면 전체 길을 알 수 있습니다.

조상 찾기는 부모만 따라가는 **깊이 우선 탐색(DFS)**을 씁니다.
방문한 번호를 집합에 적어서, 두 갈래에서 같은 조상을 만나도 한 번만 출력합니다.

### 직접 만든 정렬: 병합 정렬

큰 카드 묶음을 반씩 나누다가 한 장이 되면, 작은 카드부터 골라 다시 합칩니다.
날짜를 볼지 이름을 볼지는 `key` 함수로 바꿉니다. 파이썬 내장 정렬은 쓰지 않습니다.
값이 같으면 앞에 있던 카드를 먼저 꺼내므로 **안정 정렬**입니다.

### 빠른 검색: 역색인

예를 들어 `기능 → [00000002, 00000003]`처럼 단어마다 커밋 번호를 모읍니다.
검색할 때 모든 카드를 읽는 대신 찾아보기에 적힌 후보만 꺼냅니다.
작성자별 찾아보기도 따로 만듭니다. 같은 단어가 반복되어도 번호는 한 번만 넣습니다.

### 시간과 공간은 얼마나 필요할까?

V는 전체 커밋 수, E는 부모 연결 수, K는 검색 후보 수, L은 후보 메시지 길이입니다.
아래 설명은 딕셔너리와 집합의 평균 조회 시간이 O(1)이고 정렬 비교 비용이 일정하다고 가정합니다.

| 작업 | 시간 | 추가 공간 |
| --- | --- | --- |
| 기본 LOG (위상 정렬) | O(V + E) | O(V + E) |
| 날짜·작성자 정렬 | 평균·최악 O(V log V) | O(V) |
| PATH | O(V + E + Σ d log d), d는 방문한 각 커밋의 이웃 수 | O(V + E) |
| ANCESTORS | O(도달한 커밋 수 + 그 부모 연결 수) | O(도달한 커밋 수 + 그 부모 연결 수) |
| 작성자 검색 | 평균 O(1 + K) | O(K) |
| 단어·구절 검색 | 평균 O(검색어 길이 + K × L) | 결과 O(K), 메시지 처리 O(L) |

PATH의 추가 정렬 비용은 같은 길이의 경로를 사전순으로 고르기 위해 필요합니다.
역색인을 만들 때는 메시지를 읽고 단어마다 번호를 저장하는 시간과 공간이 필요합니다.
모든 커밋이 같은 검색 단어를 포함하면 후보도 전체 커밋만큼 많아집니다.
